# 自动化问卷填写系统 (Kotlin + Playwright) 实施计划书

## 一、 项目概述
本项目旨在开发一款高性能、支持高并发的自动化问卷填写工具。程序需根据预设的题目、选项权重概率，动态生成问卷答案，并通过 Kotlin 结合 Playwright（无头模式）实现多并发的自动化提交。

**核心技术栈：** Kotlin (协程/多线程), Playwright for Java/Kotlin.
**核心难点：** 概率算法的准确实现、多选题的概率处理、高并发下的内存泄漏控制、Playwright 实例的线程安全。

---

## 二、 数据结构与核心算法设计 (The Brain)

### 1. 输入数据解析
系统接收四个核心数据源：
*   `question` (List): 题目列表 (共10题)。
*   `option` (List<List>): 每道题对应的选项列表。
*   `Current Answer Dictionary` (List<List>): 每道题对应选项的**权重值**（默认基准为50）。
*   `typeInts` (List): 题目类型标识。**非常重要：其中 `typeInts[1] = 4` 代表第2题是多选题，其余 `3` 代表单选题。**

### 2. 概率换算与生成算法
**研发须知：** 不要在 Playwright 执行页面操作时临时计算概率，这会严重消耗性能并导致锁竞争。**必须采用“预生成机制”**。

*   **单选题 (typeInt=3) 算法：**
    *   以第一题为例权重：`[60, 50, 50, 50, 50]`。
    *   计算总权重：`60+50+50+50+50 = 260`。
    *   计算各选项概率区间：A(0.23), B(0.19), C(0.19), D(0.19), E(0.19)。
    *   生成随机数 (0-1)，根据随机数落入的区间决定选中哪一项。
*   **多选题 (typeInt=4) 算法（第2题）：**
    *   多选题的概率不能做总和归一化（不能互斥）。
    *   算法策略：将每个选项的权重独立转换为选中概率（例如 50 代表 50% 概率被选中，60 代表 60% 概率）。
    *   遍历该题所有选项，独立生成随机数判定是否勾选。**需加入兜底逻辑**：如果所有选项都没命中，强行随机勾选一个，避免多选题为空无法提交。

### 3. 数据预生成与内存缓存
*   假设用户设定**问卷数 = 100**。
*   程序启动时，在内存中瞬间生成 100 份完整的问卷答案对象 (`List<SurveyAnswer>`)。
*   将这 100 份数据推入**线程安全的数据结构**（建议使用 Kotlin 的 `Channel` 或 Java 的 `ConcurrentLinkedQueue`）中，供下游并发消费。

## 三、 并发与内存管理架构 (The Engine)

由于自动化浏览器极为消耗内存，并发控制是本项目的生死线。

### 1. 生产者 - 消费者模型
*   **生产者 (Producer)：** 根据概率算法，瞬间生成 100 份答案，存入并发队列。
*   **消费者 (Consumers / 线程数)：** 假设用户设定**线程数 = 5**。程序启动 5 个协程 (Coroutines) 或工作线程。每个工作线程从队列中 `poll()` 取出一份答案进行处理。处理完毕后，继续取下一份，直到队列为空。

### 2. 线程安全与锁机制 (Locks & Thread Safety)
研发人员需注意以下共享资源的加锁保护（建议使用 Kotlin `Mutex` 或 `AtomicInteger`）：
*   **成功/失败计数器：** 记录已成功提交了多少份，失败了多少份。
*   **队列的消费操作：** 保证同一份答案不会被两个线程同时拉取。

### 3. Playwright 内存控制（极致优化）
*   **全局单例 Browser：** 整个程序只启动**一个** `Browser` 实例（极大地节省内存）。
*   **多 Context 隔离：** 每个工作线程 (并发 = 5) 独立开辟一个 `BrowserContext` 和 `Page`。隐身模式互相隔离 Cookie 和缓存。
*   **生命周期回收 (GC 保障)：** 使用 `try-finally` 语法块。无论问卷提交成功、超时还是报错崩溃，`finally` 块中**必须显式关闭并销毁**对应的 `Page` 和 `BrowserContext`，否则 100 份问卷跑完会导致内存溢出 (OOM)。

## 四、 Playwright 网页自动化实施 (The Hands)

目前仅开启**无头模式 (Headless Mode)**。研发人员需要结合提供的 `wjx.html` 源码，实现以下精准打击：

1.  **DOM 元素定位映射：**
    *   需要编写稳健的 XPath 或 CSS Selector。例如：定位第 N 题下的第 M 个选项（Radio 或 Checkbox）。
    *   单选题执行 `click()`。多选题依次判定执行多个 `click()`。
2.  **输入防重与延时 (Anti-Bot)：**
    *   问卷星有基础的防机器检测。在答题过程中（两题之间，或点击提交按钮前），必须加入**随机延迟 (Random Delay)**，如 300ms - 800ms，模拟真人操作频率。
3.  **异常捕获与重试机制：**
    *   网络波动或元素未加载会导致异常。需设定 `TimeoutException` 捕获。
    *   失败的答案对象可选择丢弃，或重新放回队列尾部等待重试。

## 五、 全局执行工作流 (总结给研发的 Step-by-Step)

*   **Step 1[初始化]：** 读取 `question`, `option`, `Current Answer Dictionary`, `typeInts` 参数。接收用户输入的 `总问卷数 (Total)` 和 `并发线程数 (Threads)`。
*   **Step 2[数据预加载]：** 按照单选题/多选题不同的概率算法，生成 `Total` 份模拟答案列表，压入线程安全队列 `Queue`。初始化 `AtomicInteger` 用于进度统计。
*   **Step 3 [启动 Playwright]：** 初始化全局唯一的 Playwright Browser 实例（配置为 Headless）。
*   **Step 4 [并发派发]：** 启动 `Threads` 数量的 Kotlin 协程 (`Dispatchers.IO`)。
*   **Step 5 [执行自动化]：**
    *   每个协程循环从 `Queue` 获取答案。
    *   创建独立 `Context` 和 `Page` -> 访问问卷链接 -> 按答案映射点击 DOM -> 随机延时 -> 点击提交 -> 统计成功数。
    *   `finally` 关闭 `Context` 释放内存。
*   **Step 6 [收尾]：** 队列为空且所有协程结束后，关闭 Playwright 全局 Browser 实例，输出执行报告（耗时、成功率）。

**💡 给 Kotlin 研发的高级建议：**
> “开发兄弟，这个业务场景属于典型的 CPU 密集（算概率）+ IO 密集（跑浏览器）混合。请务必将数据生成的步骤放在主线程或独立逻辑中提前算好；Playwright 部分使用 `Dispatchers.IO` 跑协程。由于 Playwright 底层是阻塞的，建议使用 JUC 的 `ThreadPoolExecutor` 或者调整协程的 IO 线程池大小，并且务必处理好 `Page.close()` 的异常吞咽问题，防止僵尸进程撑爆服务器内存。”
